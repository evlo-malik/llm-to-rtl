# Report

Every number here came out of a test log or a synthesis report in this repo, on the
date given, with the commands in `README.md`. Plots: `area_fmax_vs_N.png`,
`area_per_weight.png`. Tables are regenerated by the scripts named next to them.

Date: 8 September 2026. Tools: Verilator 5.050, Icarus 13.0, cocotb 2.1.0, Yosys
0.68+136 (OSS CAD Suite, slang frontend), OpenSTA, nextpnr-himbaechel + apicula for
Gowin, sky130_fd_sc_hd tt 25C 1.8V liberty.

## 1. The array

`tb/test_top.py`, both simulators, N = 4, 8, 16. Per N: 20 weight loads with 64 rows
streamed back to back, 10 loads with random gaps, 40 loads with 1-5 rows, and the
identity / all -128 / all 127 cases. Every output bit-exact against NumPy and every
`y_valid` exactly 2N-1 cycles after its `x_valid`. The raw grid (`test_array.py`)
was checked at N = 2 and 4 with the skew done in the testbench, which checks the
`c + N + j` timing formula directly.

`syn/sweep.py`: `read_slang -> synth -flatten -> dfflibmap -> abc -constr -D 2500`,
then OpenSTA on the netlist. Fmax is register to register; the input-port paths are
listed separately because `x_vec` enters combinational logic with zero input delay.

| N | PEs | cells | area, um^2 | per PE | flops | reg-to-reg Tmin | Fmax |
|---|---|---|---|---|---|---|---|
| 2 | 4 | 1895 | 14.8k | 3.7k | 142 | 4.11 ns | 244 MHz |
| 4 | 16 | 9939 | 76.1k | 4.8k | 859 | 6.62 ns | 151 MHz |
| 8 | 64 | 47133 | 366k | 5.7k | 3895 | 7.21 ns | 139 MHz |
| 16 | 256 | 203120 | 1.59M | 6.2k | 16495 | 7.47 ns | 134 MHz |

A PE synthesised on its own is 6.0k um^2 (792 cells, 48 flops). The array averages
less per PE at small N because flattening lets synthesis see that row 0 adds to a
constant zero and that a row-i partial sum has only 16 + log2(i+1) significant bits,
so the upper rows get narrower adders and their sign-extension flops merge (N=4 has
612 flops instead of 16 x 48 + 240 skew = 1008). By N=16 most rows are deep enough to
need the full adder and the average converges on the standalone PE plus the skew
registers, which are 20 N (N-1) bits and about 6% of the area.

Fmax settles near 135 MHz: the critical path is the 8x8 multiplier plus the 32-bit
accumulate inside one PE, so it does not grow with N once the array is large enough
for fanout buffering to be the same everywhere. The 22 MHz figure the first sweep
gave at N=16 was the unbuffered synchronous-reset net fanning out to 16k flops;
letting abc buffer and size (`-constr`) removed it. A real design would register the
reset per tile.

## 2. The compiler

### Every module passes

`gen/tinygpt/run_tests.py`: 9 matrices, INT8, 8x8 arrays, each tested on 10 vectors
(zeros, all -128, all 127, two one-hots, 5 random) against `torch.nn.functional.linear`
on int64 tensors. All bit-exact. Cycles per vector are the cost of one weight-stationary
array with one weight register per PE and one vector per tile: `NT (KT (3T+2) + T)`.

| matrix | K x N | cycles / vector | MACs / cycle (of 64) |
|---|---|---|---|
| qkv | 64 x 192 | 4991 | 2.5 |
| proj | 64 x 64 | 1663 | 2.5 |
| ffwd1 | 64 x 256 | 6655 | 2.5 |
| ffwd2 | 256 x 64 | 6463 | 2.5 |
| lm_head | 64 x 65 | 1864 | 2.2 |

`gen/smollm2/run_tests.py`: SmolLM2-135M, 211 matrices, 134,479,872 weights, 16x16
arrays, RMSNorm weights folded into q/k/v/gate/up/lm_head, per-channel INT8. All 211
pass, 10 vectors each, 64 minutes of simulation wall time three at a time. Per shape:

| shape (K x N) | modules | cycles / vector | MACs / cycle (of 256) |
|---|---|---|---|
| 576 x 192 (k, v) | 60 | 21,359 | 5.2 |
| 576 x 576 (q, o) | 60 | 64,079 | 5.2 |
| 576 x 1536 (gate, up) | 60 | 170,879 | 5.2 |
| 1536 x 576 (down) | 30 | 169,919 | 5.2 |
| 576 x 49152 (tied lm_head, 28.3M weights) | 1 | 5,468,159 | 5.2 |

Full table: [SmolLM2 module results](results/smollm2_modules.md).
[Tiny GPT module results](results/tinygpt_modules.md) are also retained.

The 1-in-3T utilisation is the array starving on weight loads: every T x T tile costs
T cycles to shift its weights in and 2T-1 cycles to drain, and a decode step has only
one vector to push through it. The fix is in the PE, not the compiler: a second weight
register so the next tile shifts in while the current one is used. That is ACA L2-L6
material and the next change to `pe.sv`.

### What a weight costs (`syn/bitwidth.py`, `area_per_weight.png`)

An 8x8 and a 16x16 slice of the trained layer-0 projection, quantised to 8, 4 and 2
bits, emitted as hardwired arrays (every weight a CSD shift-add in its own cell, no
multipliers), synthesised to sky130 for area and with `synth_gowin` for LUT4 + ALU
cells; against `top.sv` of the same size.

| array | bits | nonzero of 64 | CSD adds | sky130 um^2 / weight | Gowin LUT-eq / weight |
|---|---|---|---|---|---|
| generic top.sv, 8x8 | 8 | 64 | mult | 5585 | 446 |
| hardwired 8x8 | 8 | 64 | 164 | 2302 | 78 |
| hardwired 8x8 | 4 | 55 | 81 | 1824 | 36 |
| hardwired 8x8 | ternary | 41 | 41 | 1456 | 15 |
| generic top.sv, 16x16 | 8 | 256 | mult | 6072 | 481 |
| hardwired 16x16 | 8 | 255 | 643 | 2485 | 79 |
| hardwired 16x16 | 4 | 221 | 316 | 2085 | 39 |
| hardwired 16x16 | ternary | 184 | 184 | 1870 | 20 |

Hardwiring INT8 halves the sky130 area per weight and cuts Gowin cells six-fold
(the Gowin generic number is dominated by the multiplier in LUTs and the weight
register). Going from INT8 to ternary saves a further third, not a further factor of
ten, because the cell keeps its 8-bit x register and 32-bit partial-sum register:
the 16x16 ternary array is 14k flops, 58% of its area. Registers, not multipliers,
are the floor of a systolic hardwired array. A hardwired array that dropped the
per-cell psum register for an adder tree per column would be the next experiment.

For scale: the tiny GPT has 102k weights. At 78 Gowin cells per hardwired INT8
weight that is 8M cells; the Tang Nano 20K has 20.7k. Hardwired cells are for
matrices of a few hundred weights, or for ASICs. The whole-model build therefore
keeps weights in on-chip ROM next to small generic arrays: still no DRAM in the token
loop, but the weights are read, not wired.

## 3. The model

### Training and quantisation

`model/train.py`: Karpathy's gpt.py, n_embd 64, 4 heads, 2 layers, block 32, 6000
steps, lr 1e-3, batch 64, CPU, 94 s. 110,145 parameters. Train loss 1.515, val loss
1.708 (the full-size run in the video reaches 1.48).

`compiler/check_golden.py` (64 calibration windows of 32 tokens from the training
split, 64 evaluation windows from the validation split, 2048 positions):

| weights | argmax agreement with float | cross-entropy float | cross-entropy int |
|---|---|---|---|
| INT8 per-channel | 95.3% | 1.7998 | 1.8034 |
| INT4 per-channel | 73.8% | 1.7998 | 1.9137 |
| ternary (absmean) | 24.4% | 1.7998 | 3.1556 |

The folded float model (LayerNorm affine pushed into the following Linear) matches
the torch model to 1.2e-5 in the logits, so the folding is exact and the rows above
are purely the cost of quantising. INT8 costs 0.004 nats. INT4 costs 0.11. Ternary
post-training on a model that was never trained for it is not usable, which is the
expected result; BitNet-style models train with the constraint.

### The RTL is the integer model

Unit tests, each against the same Python function `IntGPT` uses:

| unit | test | what is covered | result |
|---|---|---|---|
| requant.sv | 60 vectors, 1257 values | int32 extremes, n = 0 and 40, M0 at both ends, both widths, ReLU, bubbles | bit-exact, Verilator and Icarus |
| layernorm.sv | 67 vectors | zero variance, single spike, full-range alternating, gaussians at 4 scales | bit-exact, both simulators, 179 cycles |
| attention.sv | 2 layers x 32 positions | real layer-0 parameters and a coarse synthetic set; saturating dot products at position 5 | bit-exact, 2426 cycles per token |
| matvec_rom.sv | 7 shapes | K, N not multiples of T; T = 1; bias; 8/4/2-bit ROMs | bit-exact |

Whole model, `gen/*/tb/test_gpt_top.py`: the prompt `ROMEO:` then greedy generation
to fill the 32-token context. Every int32 logit of every position equal to `IntGPT`,
and the argmax port equal to numpy's argmax.

| build | cycles per token | RTL simulation output |
|---|---|---|
| INT8, 8x8 arrays | 51,070 | `ROMEO:\nI have so the sentleman t` |
| INT4, 8x8 arrays | 51,070 | `ROMEO:\nNow, my lord, the lords, ` |
| ternary, 8x8 arrays | 51,070 | `ROMEO: war blllle wenck warare w` |
| INT4, 2x2 arrays | 190,294 | `ROMEO:\nNow, my lord, the lords, ` |
| INT4, 1x1 arrays (the board build) | 420,726 | `ROMEO:\nNow, my lord, the lords, ` |

Where the 51k cycles go: the four matvecs of a layer are 4991 + 1663 + 6655 + 6463 =
19.8k, times two layers, plus lm_head 1.9k, is 41.5k; attention is 2.4k per layer;
five LayerNorms are 0.9k; the rest is requant, residual adds and the program. At 27 MHz
that would be 1.9 ms per token, 530 tokens per second, with the matvecs 80% of it at
2.5 MACs per cycle. The 2x2 build is 3.7x slower and the 1x1 build that fits the board
8.2x slower: with one PE per matrix the array is gone and what is left is nine serial
MAC units reading weights from block RAM, which is a fair description of what this FPGA
can hold. Double-buffered weights in the PE would bring a tile from 3T+2
cycles to about T+2 and roughly halve the token time.

### The board

`rtl/board/tang_nano_20k.sv`: UART 115200 8N1 on the USB-C bridge, a prompt FIFO,
ASCII to token tables from the compiler, `\r\n` as the end marker because the model
can emit `\n` but never `\r`. `tb/test_board.py` sends `ROMEO:` and Enter through a
UART model and reads back exactly the 26 characters `IntGPT` generates, then the
marker, and the position counter is back at 0. Passes.

Gowin synthesis and place-and-route (`syn/gowin/build.py`) of the whole design with the
UART top, GW2AR-18C: 20,736 LUT4, 15,552 flops, 46 BSRAM blocks of 18 kbit, 48 DSP
macros (96 MULT9X9 or 48 MULT18X18 BELs in nextpnr's device model).

| build | LUT4 + ALU (synth) | flops | BSRAM | multipliers | outcome |
|---|---|---|---|---|---|
| INT8, 8x8 arrays, DSP | 10266 + 18754 | 41,691 | 72 | 579 MULT9X9 | no: 3x the chip on every axis |
| INT8, 4x4 arrays, DSP | 7515 + 5457 | 11,990 | 72 | 157 | no: weight ROMs alone exceed the BSRAM |
| INT4, 4x4 arrays, DSP, bias ROM per matrix | 7165 + 5376 | 11,235 | 49 | 147 MULT9X9 | no: 3 BSRAM over, 147 > 96 MULT9X9 |
| INT4, 4x4 arrays, no DSP | 26396 + 6633 | 11,232 | 47 | 0 | no: 8x8 multipliers in LUTs cost 130 cells each |
| INT4, 4x4 arrays, DSP, bias in requant | 6614 + 5436 | 10,972 | 46 | 147 MULT9X9 | no: 147 > 96 MULT9X9 |
| INT4, 2x2 arrays, DSP, bias in requant | 4539 + 2286 | 4,168 | 46 | 39 MULT9X9 + 10 MULT18X18 | places and routes at 77.25 MHz, but apicula 0.34 cannot write the MULT18X18 fuses (`KeyError: IRBY_IREG0BL_0` in gowin_pack) |
| INT4, 2x2 arrays, no DSP, bias in requant | 15387 + 2560 | 4,168 | 46 | 0 | no: 19683 of 20736 LUT4 after packing, nextpnr cannot legalise the placement |
| **INT4, 1x1 arrays, no DSP, bias in requant** | 12581 + 2152 | 2,525 | 45 | 0 | **places, routes and packs: 66.39 MHz, bitstream written** |

After place and route the 2x2 DSP build uses 8523 LUT4 (41%), 2496 ALU, 5284 flops
(33%), 186 LUTRAM cells, all 46 BSRAM and 49 DSP BELs. nextpnr also prints ten hold-time
"violations" of about 0.1 ns on flop-to-BSRAM-address paths; they come from its Gowin
timing model, the flow passes `--timing-allow-fail`, and they should be checked against
the Gowin IDE's timing report once a board is on the desk. The build that packs is 1x1 arrays without DSPs: after place and route it uses 16469 LUT4 (79%), 2400 ALU, 3641 flops, 186 LUTRAM cells and 45 of 46 BSRAM, at 66.39 MHz; `gen/tinygpt_t1_int4/gowin/tang_nano_20k.fs` is the bitstream (7091 kB). It runs 420,726 cycles per token, so at 27 MHz the board should print about 64 characters per second. Simulated on the same generated design, `tb/test_board.py` sends
`ROMEO:` over the UART and reads back the golden model's 26 characters; the same test passes on the 1x1 build that was packed.

Two things had to move to get there, both instructive. Nine per-matrix bias ROMs of a
few hundred bits each were costing nine whole 18 kbit blocks, because an initialised ROM
can only go to block RAM in this flow (Gowin LUTRAM has no init), so the biases moved
into the requant parameter table as an 18-bit field, which cost nothing there and freed
the blocks; the logits now pass through the requant unit in an int32 mode with an
identity multiplier so their bias is applied the same way. And the multipliers set the
array size: 4x4 arrays are 144 of them against 96 DSP BELs; apicula 0.34 turned out not
to write DSP fuses for this device at all (a one-multiplier test design fails the same
way), so every multiplier has to be LUTs, where an 8x8 signed multiply is about 130
cells; 2x2 arrays then land at 94% of the LUTs and will not place. 1x1 arrays, nine
multipliers in total, are what this chip takes with this apicula. On a Tang Nano 20K
with the vendor tools, or once apicula grows the DSP fuses, the 2x2 DSP build that
already routes at 77 MHz is the one to use.

What was not done: flashing a board, tokens per second measured on a terminal, watts.
Those need the hardware.
